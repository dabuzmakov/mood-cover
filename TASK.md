# Проект 4. MoodCover

Генератор атмосферных PNG-изображений на основе алгоритма **fractal flame**
и идеи **Chaos Game**. Такие картинки музыкальный сервис мог бы использовать
для обложек плейлистов или экрана «сейчас играет»:

```text
mood-cover --width 1920 --height 1080 --iterations 2500 --seed 42 --output result.png
```

Сначала делается однопоточный рендерер, который по конфигу рисует изображение.
Затем многопоточная версия и benchmark, который честно показывает, насколько
она быстрее.

Главное в этом проекте — не картинки, а **многопоточность на честной задаче**.
Генерация упирается в процессор: сделать корректную однопоточную версию,
распараллелить её без гонок и, самое важное, **измерить** результат.

Статья про алгоритм: <https://flam3.com/flame_draves.pdf>

Задание разбито на три merge request'а. Делай их по очереди.

## MR1 — Однопоточный рендерер

- генерация точек через Chaos Game;
- аффинные преобразования;
- **минимум 4 нелинейные трансформации** на выбор: `linear`, `sinusoidal`,
  `spherical`, `swirl`, `horseshoe`, `polar`, `heart`, `disk`, ...;
- цветная генерация, накопление попаданий в пиксели;
- сохранение в PNG.

```text
Render(config, random) -> Image
```

Аффинное преобразование — шесть чисел `a,b,c,d,e,f`:

```text
xNew = a * x + b * y + c
yNew = d * x + e * y + f
```

Инварианты: `width > 0`, `height > 0`, `iterationCount > 0`, output
заканчивается на `.png`, трансформации не пусты, веса положительны, результат
воспроизводим по `seed`.

PNG пишется через **SixLabors.ImageSharp** (пакет уже подключён в
`MoodCover.App`). Это кроссплатформенная замена `System.Drawing`, которой нет
на Linux — а CI собирается именно на Linux-образе.

## MR2 — CLI, конфиг, пресеты

Параметры берутся из трёх источников, **приоритет: CLI → JSON-конфиг → дефолты**.

```text
mood-cover --seed 32 --iterations 5000 --functions swirl:1.0,horseshoe:0.8 --threads 1 --output result.png
mood-cover --config config.json
```

CLI-параметры: `--width`, `--height`, `--iterations`, `--output`, `--threads`,
`--seed`, `--functions`, `--affine-params`, `--config`, `--preset`, `--palette`.

- **пресеты настроения** (`chill`, `energy`, `focus`, `party`) задают набор
  трансформаций, палитру, итерации, размеры;
- **палитры**: `warm`, `cold`, `neon`, `pastel`, `mono`;
- расширенная валидация с понятными ошибками
  (`Error: unknown transformation: spiral`);
- логирование прогресса в адекватном количестве — не по строчке на точку.

Дефолты: `1920x1080`, `iterations = 2500`, `threads = 1`, `seed = 5`,
`preset = chill`, `palette = warm`, `output = result.png`.

Пример конфига лежит в `config/chill.example.json`.

## MR3 — Многопоточность и benchmark

- параметр `--threads`, корректное объединение результатов потоков;
- **отсутствие race condition.** Рекомендация: у каждого потока свой локальный
  буфер, слияние в конце, без общей записи. Тогда гонок не будет в принципе,
  а не «скорее всего»;
- benchmark-режим со сравнением 1, 2, 4 и 8 потоков:

```text
mood-cover benchmark --config config.json --threads 1,2,4,8 --output benchmark.md
```

Отчёт (Markdown, JSON или текст) содержит конфиг, seed, время для каждого числа
потоков, ускорение относительно одного потока и путь к PNG:

```text
| Threads | Time ms | Speedup |
| 1       | 8200    | 1.00    |
| 4       | 2900    | 2.83    |
```

**Честная оговорка.** Многопоточная версия не обязана давать пиксель-в-пиксель
тот же PNG, что однопоточная, если порядок генерации точек другой. Но при
одинаковых конфиге, seed **и числе потоков** результат обязан быть
воспроизводимым.

И не жди ускорения на маленьком числе итераций: запуск потоков тоже стоит
времени, и на короткой задаче многопоточная версия может оказаться медленнее.
Это нормальный результат, его нужно просто честно показать в отчёте.

## Тесты

В проекте **два** test-проекта: они проверяют приложение на разных уровнях.

| Проект | Что проверяет |
|---|---|
| `MoodCover.Tests` | юнит-тесты доменной логики: формулы, разбор конфига, дефолты, многопоточный рендер «в памяти». Вызывают твои классы напрямую |
| `MoodCover.IntegrationTests` | интеграционные тесты: запускают **собранный исполняемый файл** отдельным процессом (`CliRunner`) и проверяют код возврата, вывод и созданные PNG/отчёты |

Оба запускаются командами:

```text
dotnet test src/MoodCover.Tests/MoodCover.Tests.csproj        # юнит
dotnet test src/MoodCover.IntegrationTests/MoodCover.IntegrationTests.csproj  # интеграционные
```

В CI юнит и интеграционные тесты идут **отдельными шагами**: см.
`.gitlab-ci.yml`, стадия `integration`.

### Обязательные тесты

Заготовки лежат в `Mandatory/` внутри обоих проектов, разложены по merge
request'ам. Реализовать нужно все.

| Область | Что проверяем |
|---|---|
| Валидация | `width/height/iterations/threads <= 0`, пустые functions, unknown function, output без `.png` → ненулевой код возврата |
| Seed | одинаковый конфиг + seed + потоки → одинаковый результат; разный seed → разный |
| Аффинное преобразование | формула на заранее известных числах |
| Трансформации | каждая реализованная — на фиксированной точке с посчитанным вручную ожиданием |
| CLI и JSON | параметры читаются; невалидный JSON отклоняется; дефолты заполняют пропуски |
| Приоритет | JSON `threads=2` + CLI `--threads 4` → `threads = 4` |
| PNG | файл создан, не пуст, размер соответствует конфигу |
| Многопоточность | `threads = 2, 4` завершаются успешно, ненулевые пиксели, нет исключений конкурентного доступа |
| Benchmark | отчёт создан, есть строки для 1/2/4/8 потоков, время и speedup указаны |

Каждая заготовка выглядит так:

```csharp
[Fact(DisplayName = "Аффинное преобразование считается по формуле на известных числах",
      Skip = "MR1: реализуй тест и удали эту строку")]
public void AffineTransformFollowsFormula()
{
    Assert.Fail("Тест не реализован");
}
```

Удали аргумент `Skip = ...` и замени `Assert.Fail(...)` на настоящую проверку.
Названия методов и `DisplayName` менять не нужно — по ним ментор сверяется
с требованиями. Свои тесты добавлять можно и нужно, удалять обязательные — нет.

Ожидаемые значения для трансформаций считай **вручную, на бумаге**, а не
«как получилось у программы»: иначе тест зафиксирует ошибку, а не формулу.

`Skip` означает «пропущен», а не «упал», поэтому сборка зелёная с самого
начала: иначе на MR1 всё было бы красным из-за тестов MR3, и стало бы непонятно,
сломал ты что-то или нет.

### Как работают интеграционные тесты

`MoodCover.IntegrationTests/Support/CliRunner.cs` дан готовым — писать его
не нужно. Он запускает собранный `MoodCover.App.dll` отдельным процессом
(`dotnet MoodCover.App.dll <args...>`), собирает stdout/stderr и код возврата:

```csharp
var result = CliRunner.Run("--width", "0", "--output", "result.png");

Assert.NotEqual(0, result.ExitCode);
Assert.Contains("width", result.Stderr);
```

Отдельный процесс нужен, потому что иначе нельзя проверить код возврата и
поведение настоящего CLI. `System.Exit` в .NET тоже завершает процесс теста,
поэтому вызывать `Program.Main(...)` прямо из теста нельзя.

## Что делать НЕ нужно

GUI, веб-сервис, база данных, редактор изображений, интерактивная настройка
в реальном времени, фотореалистичность, все известные flame-трансформации,
гарантия ускорения на маленьком числе итераций.
